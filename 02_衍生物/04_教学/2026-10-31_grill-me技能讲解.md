## 一、一句话定位

**grill-me 是一个"开工前的对齐工具"**：它不产出任何代码或文档，只做一件事——
在动手之前，把你脑子里的计划逐条掰开、追问到底，直到没有"看情况再说"的悬空项。

它的产出只有一样东西：**一张决策表**（每个分支选了什么）。

## 二、来源与血统：它在作者的技能体系里站在哪

### 2.1 作者与仓库

| 项 | 内容 |
|---|---|
| 作者 | **Matt Pocock**（GitHub: `mattpocock`） |
| 仓库标语 | *"Skills for Real Engineers. Straight from my .agents directory."* |
| 作者自述 | *"My agent skills that I use every day to do real engineering — **not vibe coding**."* |
| 规模 | 共 **27 个技能** = Engineering（工程类 20 个）+ Productivity（效率类 7 个） |

### 2.2 关键分类：谁可以调用

作者把技能按**调用方式**分成两类，这是理解整个体系的钥匙：

| 类别 | 谁能触发 | 职责 | 数量 |
|---|---|---|---|
| **User-invoked** | 只能你显式输入（如 `/grill-me`） | **编排 / orchestrate** | Engineering 11 + Productivity 5 |
| **Model-invoked** | 你可调，agent 在任务匹配时也**可自动触及** | 承载**可复用纪律 / reusable discipline** | Engineering 9 + Productivity 2 |

> **铁律**：User-invoked 技能可以调用 Model-invoked 技能，
> 但**绝不能调用另一个 User-invoked 技能**。

**grill-me 属于 Productivity / User-invoked** —— 即：它是通用（非代码）入口，必须由你点名才能启动，职责是编排。

### 2.3 它的底层引擎：`grilling`

仓库里有一个 Model-invoked 原语叫 **`grilling`**，它是"访谈引擎"本身。
下面这些 User-invoked 技能**共用**它：

```
                    ┌─ grill-me
                    ├─ grill-with-docs
   grilling ────────┼─ triage
（model-invoked原语）├─ wayfinder
                    └─ improve-codebase-architecture
```

所以 grill-me 不是一个孤立脚本，而是**五个上层技能共享的同一个内核的一个入口**。

### 2.4 它为解决什么问题而生

作者总结了 agent 协作的**四大失败模式**，grill-me 专门对应第 1 条：

| # | 失败模式 | 作者引述 | 对应解法 |
|---|---|---|---|
| **1** | **Agent 没做我想要的事** | *The Pragmatic Programmer*：**"No-one knows exactly what they want"** | **grill-me / grill-with-docs** ← 本技能 |
| 2 | Agent 太啰嗦 | Eric Evans《DDD》的 ubiquitous language | 建立 `GLOSSARY.md` 共享词汇表 |
| 3 | 代码跑不起来 | *"The rate of feedback is your speed limit"* | `tdd` 红-绿-重构 / `diagnosing-bugs` |
| 4 | 建成一个泥球 | Kent Beck：*"Invest in the design of the system every day"* | `codebase-design` 深模块 / `improve-codebase-architecture` |

一句话：**grill-me 是作者对"人类自己也没想清楚就要开工"这个根因的处方。**

### 2.5 版本漂移（一个真实观察）

本地 `SKILL.md` 在讲与 grill-with-docs 的区别时，写的是 `CONTEXT.md`。
而 GitHub 仓库现行命名是 **`GLOSSARY.md`**（仓库文档明确说 `CONTEXT.md` 是**早期约定名**）。

**结论：你本地装的是较早版本（v1.0.0），与仓库主线存在轻微漂移。**
这不影响使用，但引用术语时以本地文件为准。

## 三、设计解析：为什么是这四条规则

`SKILL.md` 的核心只有四段规则，每一段都有明确的设计意图：

| 规则原文要点 | 设计意图 |
|---|---|
| **先给推荐答案，再提问** | 降低你的决策成本。没推荐项时，人容易停在"不知道选哪个"；有推荐项后，你只需要"同意或否决" |
| **问完必须等回答，再进入下一题** | **强制串行**。决策之间有依赖，并行问会把依赖关系搞丢 |
| **能自己查出来的，别问用户** | 避免把"可推导的事实"变成你的负担。这一条在本次会话里起了决定性作用（见 §6） |
| **停下来的条件：所有分支走完、没有"看情况"** | 给了明确的终止信号，避免无限追问 |

**会话结构**也定死了五步：

1. 列出方案的顶层决策分支（3–6 个）
2. **先挑最基础的那个分支**（其他分支往往依赖它）
3. 一个分支走完再走下一个
4. 分支内部按依赖顺序解决子决策
5. 收尾用**一段话**总结关键决策

### 设计上的两个"克制"

- **不读也不写文档**（原文：*"No documentation is read or updated"*）
  → 这是它和 `grill-with-docs` 的分水岭。
- **只声明了 Read 和 Grep 两个工具**
  → 作者刻意限制它的手，让它只能"看"不能"做"。

## 四、运行原理

把它抽象成一台状态机：

```
启动
  │
  ├─ ① 枚举决策分支（3–6 个）并展示给你
  │
  ├─ ② 选最基础的分支
  │      │
  │      ├─ 该问题能否自己查到答案？
  │      │     是 → 自己去 Read/Grep，直接填，不打扰你
  │      │     否 → 先给推荐项 → 提问 → 【阻塞等待你的回答】
  │      │
  │      └─ 分支内子决策按依赖顺序递归展开
  │
  ├─ ③ 该分支收敛 → 回到 ②，处理下一个分支
  │
  └─ ④ 全部分支收敛且无悬空项 → 一段话总结 → 结束
```

**它的"智能"不在算法，在于把隐性假设逼成显性问题。**

## 五、能力边界

### 能做到

- 把一个模糊计划拆成 3–6 个可决策的分支
- 强制按依赖顺序串行收敛，避免"边做边改"
- 逼出你没意识到的隐性假设和取舍
- 产出一张可追溯的决策表（谁在哪个分支选了什么）
- 替你去查那些"明明可以查到"的事实，减少你的负担

### 做不到（重要）

| 不能 | 说明 |
|---|---|
| 不写任何文档 | 明确禁止。要落文档得用 `grill-with-docs` |
| 不改代码、不执行命令 | 只声明了 Read/Grep |
| 不保证结论正确 | 它只保证**决策被显式化**，不替你做技术判断 |
| 不跨会话延续 | 结束即结束，产物只存在于当次对话 |

## 七、与 WorkBuddy 平台的交互（本次会话解答过的真实疑问）

### 7.1 技能说"不写文档"，但日志文件还是出现了

你问过：**"日志是你自带的还是插件影响？"**

答案是**平台自带的，与 grill-me 无关，甚至方向相反**：

- grill-me 明确规定 **不读不写文档**
- 但 WorkBuddy 平台有**内建的记忆机制**，会在完成实质工作后自动落地 `.workbuddy/memory/YYYY-MM-DD.md`
- 两者是**不同层面**：技能约束的是**我在这次对话里做什么**，平台机制决定的是**工作区留什么痕迹**
- **技能禁令不会覆盖平台机制**

完整机制见 `04_教学/2026-10-30_WorkBuddy记忆体系讲解.md`。

### 7.2 一句话总结这次的教训

> **产物的正确性来自算法与验证，不来自技能本身。**
> 本次真正保住质量的是两件事：
> ① 用反推算法重新生成原有 8 组数据、逐格比对（约 300 行只差 4 处笔误）；
> ② 后来补做的**格式保真审计**（发现首版把彩色字体全抹黑了 375 处）。
> grill-me 负责的是"做之前想清楚"，它不负责"做出来对不对"。
